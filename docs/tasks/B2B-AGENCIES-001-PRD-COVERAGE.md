## تصمیم‌ها و محدوده این پیگیری

- تصمیم صریح مالک: **سقف مستقل برای هر ارز؛ بدون تبدیل خودکار**. محاسبه فقط
  با ارز یکسان انجام می‌شود. مدل موجود هنوز یک سیاست اعتبار به‌ازای پروفایل
  دارد؛ نگهداری هم‌زمان چند سیاست ارزی به migration افزایشی نیاز دارد.
- پاسخ تعیین زمان تحقق پورسانت و ماتریس تأیید هنوز دریافت نشده است. پاسخ سؤال
  ارز به معنی تأیید دو سؤال دیگر نیست. جدایی پیشنهاددهنده و تأییدکننده طبق
  درخواست اصلی لازم است؛ تعداد مراحل و مجوزهای تأیید هنوز نهایی نیست.
- ترکیب Exposure، قواعد تقدم تجاری/مارکتینگ، نگهداری قانونی اسناد، مالیات و
  تجمیع فاکتور و اهداف عملیاتیِ بازِ خود PRD نیز تصمیم نهایی ندارند.
- حذف دائمی درخواستی مالک با FR-ORG-04 سازگار است: حذف هویت بدون وابستگی از
  API مالک، با نسخه و تأیید صریح؛ هویت دارای وابستگی تجاری با FK محدود می‌شود.
  تاریخچه فروش یا مالی حذف آبشاری نمی‌شود.
- آخرین وضعیت منتشرشده بررسی شد: PR90 ادغام شده، PR112 باز است و سند
  `RESERVATIONS-001A.md` آن هیچ قفل مشترکی مطالبه نمی‌کند. قفل‌های تاریخی را
  دائمی فرض نمی‌کنیم؛ این پیگیری schema یا قرارداد مشترک جدید رزرو نکرده است.
  محدودیت واقعی پذیرش، قابلیت‌های اجرا‌نشده و تصمیم‌ها/قراردادهای مالک است.

## تکمیل‌های این پیگیری

۱. تب اسناد به API عمومی Documents متصل شد: فهرست صفحه‌بندی‌شده، شعبه مجاز،
فیلتر انقضا و بارگذاری فایل. مرجع قفل‌شده
`master-data / organizations / organizationId` و دامنه `ORGANIZATION` است؛
لوگوی BRAND و مدارک مشتریان وارد این فهرست نمی‌شوند. اندازه/MIME، نوع، مالک،
دسته، شعبه، تاریخ و مجوز پیش از ارسال کنترل می‌شوند؛ Backend مالک بررسی نهایی،
قرنطینه، رمزنگاری، طبقه‌بندی و Audit است. مشاهده نسخه‌ها، ویرایش metadata و
دریافت فایل از صفحه واقعی Documents با کنترل‌های همان مالک انجام می‌شود.
بارگذاری مبهم خودکار تکرار نمی‌شود؛ فایل و ورودی فرم پس از خطا حفظ می‌شوند.

۲. پیش‌نویس توافق‌نامه می‌تواند سند سازمان را انتخاب کند. Backend از Service
عمومی Documents تعلق سند به سازمان و شعبه، دامنه، مجوز، تکمیل، تاریخ و اسکن
موفق را بررسی می‌کند؛ UUID نامرتبط یا فایل قرنطینه‌شده پذیرفته نمی‌شود.
این مرجع **اثبات امضا یا snapshot نسخه غیرقابل‌تغییر نیست**. FK محافظت‌کننده
سندِ استفاده‌شده و اتصال نسخه قطعی هنوز در مدل نهایی لازم است.

۳. نمایش اعتبار ثبت‌شده، مصرف مالی، اختلاف دقیق، ارز، زمان و نسخه منبع اضافه
شد. محاسبه با رشته Decimal/BigInt انجام می‌شود؛ ارز متفاوت، داده نامعتبر، زمان
آینده، سیاست منقضی یا فقدان منبع، نتیجه قابل‌استفاده تولید نمی‌کند. مقدار منفی
به صفر تبدیل نمی‌شود. این نما مجوز ثبت سفارش نیست و اجزای Exposure/اعتبار موقت
را که قرارداد عمومی ندارد، اختراع نمی‌کند.

۴. مسیر قدیمی ایجاد پروفایل فعال بسته شد: وضعیت اولیه `UNDER_REVIEW` و تغییر
چرخه وضعیت تا آماده‌شدن تأیید پایدار رد می‌شود. کنترل زیر قفل تراکنشی انجام
می‌شود. سازمان غیرفعال قابل تغییر نیست. ویرایش metadata وضعیت، غیرفعال‌شدن و
مدیر حسابِ ارسال‌نشده را بازنویسی نمی‌کند؛ optimistic version و audit حفظ شدند.

## قواعد، قراردادها و نیازمندی‌های غیرعملکردی

- BR01–02: هویت مشترک و عدم نوشتن مانده رعایت شده؛ پروفایل‌های مستقل نقش باقی‌اند.
- BR03–04: تاریخ/version و overlap نرخ موجود؛ immutable version و resolver عمومی ناقص‌اند.
- BR05: باینری فقط در Documents؛ حفاظت FK از document-version استفاده‌شده هنوز ناقص است.
- BR06: تماس از API ماسک‌شده Master Data خوانده می‌شود؛ unmask و audit مالک حفظ می‌شود.
- BR07: هیچ هویت دامنه دیگری کپی نشد؛ Referenceهای جدید HR/Customer/IAM هنوز ساخته نشده‌اند.
- BR08–09: مالی و تخفیف ماژول‌های دیگر نوشته نمی‌شوند؛ اجرای Rule/Accrual کامل نیست.
- BR10: تاریخچه تجاری حذف آبشاری نمی‌شود؛ workflow خاتمه هنوز وجود ندارد.
- BR11: Decimal/ارز و UTC موجود؛ سیاست اعتبار بدون تبدیل خودکار ثبت شد.
- BR12: سرویس عمومی برای اتصال‌ها؛ outbox رویدادهای B2B هنوز وجود ندارد.

NFR01 بخشی: write/audit تراکنشی، optimistic lock و serialization موجود؛
idempotency پایدار فعال‌سازی/تغییر/تسویه اجرا نشده است. NFR02 و NFR04 اندازه‌گیری
و read model گزارش تأییدشده ندارند. NFR03 در مدل‌های موجود رعایت می‌شود.
NFR05 خروجی کوچک XLSX واقعی است؛ job حجیم/لینک منقضی‌شونده نداریم.
NFR06 RTL، modal و کنترل‌های فرم وجود دارند؛ این پیگیری ادعای audit کامل WCAG
یا آزمون ظاهری موفق ندارد. NFR07 قراردادهای موجود v1 حفظ شدند؛ semantics
پروفایل سخت‌گیرانه‌تر شده و مصرف‌کننده باید همراه API به‌روز شود.
NFR08 هیچ فایل/PII/credential واقعی به Git یا fixture اضافه نشد؛ داده تست مصنوعی است.

API/Eventهای `validateTerms`, `resolveCommercialTerms`, `validateCredit`,
`getOrganizationExposure`, `requestConsolidatedInvoice` و رویدادهای lifecycle
B2B هنوز قرارداد اجرایی یکپارچه ندارند. بررسی آخرین develop نشان داد
`packages/contracts/src/finance/index.ts` صریحاً `finance.v1-proposal` و بدون
persistence/posting/approval اجرایی است. این نقص در مصرف‌کننده با داده ساختگی
یا query مستقیم جدول Finance جبران نمی‌شود.

## پذیرش و کار بعدی

AC01، AC04، AC09–12 فقط بخشی پوشش دارند؛ AC02–03 و AC05–08 کامل نیستند.
بدون تکمیل این موارد، برچسب «کل PRD پیاده شد» صحیح نیست.

ترتیب فنی باقی‌مانده: تصمیم‌های P0 → رزرو تازه schema/contracts بر مبنای مشترک
فعلی → migration افزایشی profile(role)، referenceهای واقعی و version/history/
approval/idempotency/outbox → اتصال HR/IAM/Customers → شرایط تجاری و snapshot
Sales → projection و کنترل اعتبار Finance → travel/settlement/disputes →
گزارش و تست پذیرش هم‌زمانی/مجوز/بار. مدل نهایی اعتبار باید unique scope ارز
داشته باشد و هیچ FX ضمنی در محاسبه وارد نکند. Branch فعلی بدون merge/rebase
حفظ شده است؛ مبنای قدیمی آن مدل HR جدید را ندارد.

نتیجه نهایی تست‌ها و وضعیت انتشار در [گزارش اجرای همین وظیفه](B2B-AGENCIES-001.md)
ثبت می‌شود. فایل Word اصلی و backup خصوصی دیتابیس به Repository اضافه نشده‌اند.
