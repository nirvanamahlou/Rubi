# B2B-PHONE-VERIFICATION-1003 — frozen contract v1.1

Owner PC-B. Scope: cooperation registration wizard only. An entered phone is optional; if supplied it requires a dedicated verification step and server-verified contact command. Generic administrative contact CRUD elsewhere remains unchanged and does not acquire a verified claim. This is phone-code verification, never company KYC/IAM authentication.

User chose development-only visible test code. All challenge, verify and verified-contact commands fail closed unless NODE_ENV is exactly development. No real SMS is sent, no provider secret/credential is introduced. Future SMS.IR plugs into a delivery interface; production needs real delivery plus durable atomic challenge storage before enabling. Current memory storage is bounded development simulation, not production infrastructure.

Invariants:
- Normalize Persian/Arabic digits and Iranian mobile09/+98/0098 to canonical+989xxxxxxxxx; reject other inputs and explain supported number in UI.
- Authenticated actor (and session if available), fixed registration purpose, draft requestId and canonical phone bind challenge/grant. No client verified boolean is trusted. New route/service enforce current existing master_data.read/create and valid actor branch/portal boundary; do not widen permissions.
- Cryptographic random code; only digest stored. Five-minute code expiry, at most five failed attempts, 60-second resend cooldown and bounded actor/phone hourly budgets. Capacity refusal never evicts active rate limits to bypass quotas.
- Resend invalidates previous challenge and grant. Verification yields unguessable expiring single-use grant. Consume/claim synchronously before persistence await; do not restore after ambiguous failure. Reject wrong actor/phone/draft, expired/replayed/concurrent grants. Check limits server-side.
- Verify never persists the phone. Dedicated verified-contact command delegates to public MasterDataService only after grant validation and existing authorization. No direct cross-module table access/schema change. Preserve current partial-save handling, do not silently retry a consumed grant.
- Changing phone/draft invalidates UI verification. Stale request/verify responses must not verify a changed phone or closed form. Save is gated in UI and backend; grant included only for its exact phone/draft. Empty optional phone follows existing contact flow.
- Codes/grants absent from normal logs/audit/Git. Development-only code response/UI label explicit; no development code in production responses.

Acceptance: normalization, expiry boundary, attempts, cooldown/resend invalidation, quotas/capacity, actor/draft/phone mismatch, missing permission/portal access, replay/concurrent create, persistence failure with consumed grant, all production gates, optional phone, changed phone/stale response, existing registration contracts/uploads unaffected. Independent read-only security review required against final candidate. Push/PR follow repository policy; no merge/runtime rollout requested in this user turn.

Frozen limits: max20 sends per actor/hour, max5 sends per canonical phone/hour, max1000 active store security entries (fail closed at capacity), 60s resend. Grant TTL5min. Bind actor userId, active branch, registrationId, role and existing organizationId if selected; arbitrary organization creation is allowed only for a grant issued for new registration. Challenge replacement invalidates grants for that actor+registration. Persistence failure spends grant; recovery message instructs new code and checking the partial dossier. Add Cache-Control:no-store. Observer advice OTP-A01 scope resolved; OTP-A02/A03/A04 mandatory acceptance invariants.

Validate existing active organization and bind its id; role may be checked at consume after the existing save adds it. Changing draft means changing registrationId/identity context (phone, role, new/existing mode, selected existing org), not unrelated address/contract edits in later stages.
