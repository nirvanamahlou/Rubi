# CI-001 — CI مشترک PC-A و PC-B

وضعیت: `IN_PROGRESS`

## هدف

یک GitHub Actions workflow مشترک و تکرارپذیر برای تمام Branchها و Pull Requestهای
PC-A و PC-B ایجاد شود. CI روی runner موقت اجرا می‌شود و به Checkout، سرور، دیتابیس یا
فایل‌های محلی هیچ‌کدام از دو کامپیوتر دسترسی ندارد.

## محدوده

- `.github/workflows/ci.yml`
- Prettier فایل‌های تغییرکرده و Full lint/typecheck/test/build کل Monorepo
- Prisma format/validate/generate
- اجرای Migrationها و Seed دوگانه روی PostgreSQL 18 موقت
- Concurrency مستقل بر اساس Head Branch
- Permission حداقلی و عدم استفاده از Secret تولیدی

## خارج از محدوده

- CD، Staging یا Production deployment
- Docker image انتشارپذیر، Nginx، DNS و TLS
- تغییر Schema، Migration، Seed، source code یا dependency
- تغییر Branch، Worktree، پردازش یا دیتابیس محلی PC-A/PC-B

## قواعد عدم تداخل

1. کلید concurrency از Head Branch محاسبه می‌شود؛ Push جدید فقط اجرای قبلی همان
   Branch را لغو می‌کند.
2. شاخه‌های `codex/pc-a-*` و `codex/pc-b-*` Workflow یکسانی دارند و هیچ شرطی نتیجه
   یکی را به دیگری وابسته نمی‌کند.
3. سرویس PostgreSQL و تمام داده‌های CI داخل runner موقت و synthetic هستند.
4. CI هیچ push، merge، commit، deploy یا mutation روی Remote انجام نمی‌دهد.
5. `GITHUB_TOKEN` فقط مجوز `contents: read` دارد و credential checkout persist نمی‌شود.

## معیار پذیرش

- Workflow از نظر YAML و قرارداد Repository معتبر باشد.
- Full lint کل Monorepo و نه فقط فایل‌های تغییرکرده اجرا شود.
- بدهی قالب‌بندی فایل‌های قدیمی مانع کار Branchها نشود و Prettier فقط فایل‌های
  تغییرکرده همان Push/PR را کنترل کند.
- Node و pnpm دقیقاً با قرارداد Repository هماهنگ باشند.
- Migrationها از صفر اجرا و Seed دو بار بدون خطا اجرا شود.
- اجرای Branchهای مختلف concurrency group جدا داشته باشد.
- Workflow برای PRهای stacked با Base شاخه PC-A/PC-B نیز فعال باشد.
- کنترل‌های موجود Repository در محیط محلی این Branch پاس شوند.
