# HR-PUBLISH-012 — تحویل انتشار منابع انسانی به PC-A

`COMPUTER_ID=PC-B`؛ درخواست صریح مالک در 2026-09-09: پوش، مرج و در دسترس بودن تغییرات برای PC-A. محدوده انتشار شامل [PR125](https://github.com/nirvanamahlou/Rubi/pull/125) برای دکمه‌های عملیات و [PR127](https://github.com/nirvanamahlou/Rubi/pull/127) برای ارتباط هزینه و مأموریت است. انتشار به `develop` مشترک انجام می‌شود؛ `main` و اجرای محلی آژانس‌ها جزو این کار نیستند.

شاخه‌ها با Merge معمولی به develop جاری متصل شده‌اند. کد HR با منبع آزموده‌شده `13b6f495793839e6cba326743f382e48b08686da` یکسان است؛ تغییرات آژانس‌ها، اسناد و دیگر ماژول‌ها از develop حفظ شدند. تنها تعارض‌های افزایشی `WORK_ASSIGNMENTS.md` و `docs/PROJECT_STATUS.md` با نگه‌داشتن هر دو سوابق رفع شدند؛ تغییرات جدید این انتشار فقط همین هماهنگی و راهنمای دریافت است.

۹۹ تست HR وب و ۸۰ تست API شامل ۲۱ PostgreSQL مستقل، lint/typecheck و Build تولیدی قبلاً برای منبع HR موفق بوده‌اند؛ پس از اصلاح نهایی رفت‌وبرگشت پرونده نیز ۲۱ تست مرتبط و Build تکرار شدند. CI ترکیبی هر PR باید چهار مرحله کیفیت، تست کامل، Build کامل و PostgreSQL را با موفقیت تمام کند. شواهد نهایی و Merge commit در همان PRها و اجرای CI روی develop قابل مشاهده‌اند.

برای کنترل دریافت کد در PC-A، از مخزن فعلی آن دستگاه اجرا شود:

```powershell
git status --short --branch
git remote -v
git fetch --prune origin
git log -1 --oneline origin/develop
git merge-base --is-ancestor 13b6f495793839e6cba326743f382e48b08686da origin/develop
```

Remote باید همان `https://github.com/nirvanamahlou/Rubi.git` باشد. پس از Merge PR127، خروجی آخر باید کد خروج صفر باشد؛ این یعنی هر دو تغییر HR در نسخه مشترک وجود دارند. برای ادامه کار، develop جدید با روال معمول وارد شاخه کاری PC-A شود. اگر تغییر ثبت‌نشده یا کار مستقلی در checkout وجود دارد، از همان worktree استفاده یا آن را بازنویسی نکنید؛ یک worktree تازه و شاخه مستقل مطابق `docs/DEVELOPMENT_WORKFLOW.md` بسازید.

برای مشاهده تغییر در برنامه، Web و API روی خود PC-A باید از همان منبع Build و با تنظیمات محلی موجود آن دستگاه اجرا شوند. Git داده‌های محلی، فایل‌های آپلودشده یا تنظیمات محرمانه PC-B را همگام نمی‌کند. این دو تغییر Migration جدید ندارند؛ نسخه‌های عقب‌مانده‌تر باید migrations قبلاً منتشرشده را از مسیر معمول انتشار و پس از بررسی وضعیت محلی اعمال کنند. هیچ Reset، Seed، تغییر گذرواژه یا مجوز جدید برای این اصلاح لازم نیست.

پذیرش عملکردی: در «مأموریت و هزینه‌ها ← هزینه‌های مستقل ← ثبت هزینه مستقل»، شرکت را انتخاب کنید؛ مأموریت‌ها با کد، کارمند، مقصد و تاریخ نمایش داده می‌شوند. انتخاب مأموریت، کارمند را تکمیل می‌کند؛ تغییر کارمند مرجع قبلی را پاک می‌کند. هزینه پیش‌نویس امکان ویرایش مرجع دارد و از پرونده هزینه می‌توان به پرونده مأموریت برگشت. اطلاعات هزینه باید با مأموریت همان شرکت و کارمند مرتبط بماند.

ابزارهای این تسک و «PC-B Uniting» فقط PC-B را می‌بینند. انتشار در مخزن قابل راستی‌آزمایی است؛ تأیید fetch، Build و مرورگر خود PC-A نیازمند خروجی همان دستگاه است. هیچ سرویس، داده یا فایل محیطی PC-A در این انتشار تغییر داده نشده است.
