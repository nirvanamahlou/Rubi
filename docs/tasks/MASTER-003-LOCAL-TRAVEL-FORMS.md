# فرم ترانسفر و ویزا — PC-B

وضعیت: آماده Review؛ انتشار با تأیید کاربر در 2026-08-31 روی `codex/pc-b-master-data-travel-form-details`، Stacked روی حذف امن. Migration افزایشی پس از Backup روی دیتابیس محلی اجرا شد؛ گزارش زیر نتیجه مرحله پیاده‌سازی مستقل است.

## قرارداد افزایشی

Producer و Consumer همان Master Data API/Web هستند؛ نسخه v12 و endpointهای
POST/PATCH فعلی حفظ می‌شوند. هیچ داده عملیاتی مسافر یا نرخ/رزرو ساخته نمی‌شود.

- `transfer-types`: ستون اختیاری `suggestedCapacityMin` حداقل بازه است؛ ستون قبلی
  `suggestedCapacity` همچنان سقف ظرفیت ۱ تا ۱۰۰ نفر است. حداقل بدون سقف و حداقل
  بزرگ‌تر از سقف در API و DB ممنوع است. نبود حداقل همان نمایش قدیمی «تا ... نفر» است.
- `visa-services`: `referenceValidityMode` با مقدار پیش‌فرض `DAYS` یا مقدار
  `PASSPORT_EXPIRY` افزوده می‌شود. حالت دوم فقط سیاست مرجع است؛ تاریخ یا شماره
  پاسپورت ذخیره نمی‌شود و `referenceValidityDays` باید null باشد.
- `values.status` اختیاری برای دو منبع فوق با کنترل `master_data.status.manage`
  همراه سایر مشخصات در یک تراکنش/نسخه/Audit ذخیره می‌شود. نبود آن رفتار قبلی را حفظ می‌کند.
- کد فقط‌خواندنی است. شمارش استفاده قابل ثبت دستی نیست؛ تا قرارداد واقعی رزرو،
  نمایش عدم دسترسی جایگزین عدد ساختگی یا صفر می‌شود. راهنمای ویزا همان شناسه عمومی
  Documents است؛ این اصلاح آپلود سند متقاضی یا اتصال جعلی Documents ایجاد نمی‌کند.
- PATCH فقط فیلدهای حاضر را تغییر می‌دهد؛ قواعد چندفیلدی با مقدار ذخیره‌شده سنجیده
  می‌شوند و FK کشور/Provider، مجوزها و کنترل نسخه باقی می‌مانند.

## حفظ داده و اجرا

Migration فقط دو ستون و CHECK اضافه می‌کند؛ ستون/ردیف فعلی حذف یا بازنویسی نمی‌شود.
Rollback رابط با حفظ API اعتبارسنج و ستون‌های افزوده، مسیر کم‌ریسک بازگشت است؛
API قدیمی قواعد حالت پایان پاسپورت را نمی‌شناسد، پس بازگشت کامل Backend نیازمند
بررسی جداگانه رکوردهای حالت جدید است. حذف ستون دارای داده نیازمند نسخه پشتیبان و
تأیید جداست. برگشت DDL فقط روی دیتابیس موقت مجاز است و در محیط کاربردی اجرا نشد.

تغییرات فرم تور، همکاری، حذف امن و مسیر درختی حفظ می‌شوند. Branch، سرور، Session و
Dependency تغییر نمی‌کنند.

## نتیجه بررسی

- API هدفمند: `travel-reference-form.spec.ts`، تست موجود travel-services و نوع تور: ۷۰ موفق.
- Web مدل/فرم واقعی SSR: ۲۸ موفق؛ شامل تمام عنوان‌ها، کد/استفاده فقط‌خواندنی، راهنمای فیلد، پاک‌کردن انتخاب‌ها و مخفی‌شدن تعداد روز در حالت پایان پاسپورت.
- PostgreSQL 18 جدا: تمام Migrationها اجرا شدند، سپس ۱۳ تست واقعی حفظ رکورد قدیمی، ذخیره رفت‌وبرگشتی، وضعیت مجوزدار، stale version، Audit اتمیک و CHECK/FK موفق شدند. دیتابیس موقت فقط شامل داده تست بود و پس از آزمون حذف شد؛ داده کاربردی حذف نشد.
- دو تست ساختار Migration، Prisma format/validate/generate در نسخه جدا، ساخت Client جدا، lint فایل‌های متاثر، Web typecheck و ساخت API با خروجی جدا موفق‌اند.
- ۱۴ تست Contracts، `git diff --check` و بررسی الگوهای Credential در ۹ فایل جدید کد/آزمون/Migration نیز موفق‌اند. آزمون PostgreSQL فقط با `RUBI_RUN_TRAVEL_FORM_POSTGRES_TESTS=1`، یک worker و `--testTimeout=30000` اجرا می‌شود؛ `RUBI_TRAVEL_TEST_DATABASE_MODULE` امکان استفاده از Client ساخته‌شده در مسیر موقت را دارد.
- Production Build کامل Web نیز در کپی موقت با خروجی مستقل موفق شد؛ cache/خروجی سرور جاری جایگزین نشد. آخرین تغییر پس از این Build فقط ترجمه برچسب راهنما در Popup ویزا بود.
- بررسی Schema با ابزار `database-designer`: دو ستون و سه CHECK افزایشی، بدون حذف/تغییر نوع. هشدار index ابزار به‌دلیل نخواندن indexهای JSON است؛ indexهای واقعی کشور و Provider در Migration قبلی موجودند. ابزار تولید طرح مشکل serialization dataclass داشت؛ با wrapper موقت، بدون تغییر فایل Skill، طرح و validation تولید شد. SQL تولیدی ابزار به‌دلیل identifierهای camelCase بدون quote مستقیماً اجرا نشد؛ Migration خود پروژه با quote صحیح روی PostgreSQL آزموده شد.
- مجموعه گسترده Master Data در زمان بررسی: API با ۳۲۶ موفق و دو شکست مربوط به آرایه `terminalType`/`airportId`؛ Web با ۲۴۱ موفق و یک شکست انتظار سه نوع ترمینال در برابر چهار نوع جدید. typecheck کل API نیز از تست جدید ترمینال و Client مشترک قدیمی برای `MIXED` خطا گرفت. این موارد در فایل‌های کار هم‌زمان دیگری هستند و در این اصلاح تغییر داده نشدند.
- Smoke احراز‌شده روی محیط مشترک انجام نشده؛ اجرای موفق فرم با دیتابیس مشترک پیش از فعال‌سازی ادعا نمی‌شود. Secret، نرخ ساختگی یا اطلاعات واقعی متقاضی به Seed یا کد افزوده نشد.

## فعال‌سازی با هماهنگی محیط مشترک

1. Migrationهای معلق را بررسی کنید؛ Migration جدید ترمینال متعلق به کار هم‌زمان دیگری است و نباید ناخواسته در همین عملیات Deploy شود.
2. Migration افزایشی این فرم‌ها را در محیط هدف اعمال و Prisma Client/بسته Database را بازسازی کنید.
3. پس از هماهنگی، API را با Client جدید بارگذاری کنید؛ سپس ذخیره/ویرایش فرم‌های ترانسفر و ویزا و تغییر وضعیت را در Web احراز‌شده تست کنید.

کد Web جدید نباید پیش از Migration و Client جدید به‌عنوان نسخه فعال نهایی تحویل شود.
هیچ Branch، Commit، Push، سرور یا تنظیمات Session در این گفت‌وگوی جانبی تغییر داده نشده است.
