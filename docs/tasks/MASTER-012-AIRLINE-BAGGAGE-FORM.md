# MASTER-012 — قواعد بار در فرم ایرلاین

## رفتار تحویلی

- زیرناوبری مستقل «قواعد بار» حذف می‌شود. افزودن، ویرایش و غیرفعال‌سازی قاعده در همان فرم ایرلاین است؛ پروفایل ایرلاین نیز قواعدش را فقط‌خواندنی نشان می‌دهد.
- پس از ایجاد ایرلاین، همان Dialog به حالت ویرایشِ رکورد ذخیره‌شده می‌رود تا قواعد با FK واقعی ثبت شوند. هیچ قاعده‌ای پیش از داشتن شناسه پایدار ایرلاین نوشته نمی‌شود.
- هر قاعده نوع مسافر `ADT`/`CHD`/`INF`، کلاس پروازی اختیاری (قاعده عمومی یا کلاس مشخص)، دامنه مسیر، مقدار Decimal، واحد و تعداد قطعه را جداگانه دارد. ترکیب فعال تکراری در UI رد می‌شود؛ API موجود همچنان اعتبارسنجی دامنه و نسخه را enforce می‌کند.
- عنوان فارسی از فرم قواعد بار حذف شد. ستون داخلی `name` برای سازگاری Backend خودکار از کد ایرلاین، کد نوع مسافر، کد کلاس و دامنه مسیر با متن انگلیسی ساخته می‌شود؛ داده نمایشی نمونه نیز انگلیسی است.
- قاعده در رکورد ایرلاین کپی نمی‌شود و همان `MasterBaggageRule` موجود با ارتباط `airlineId`/`cabinClassId` برای مصرف‌کنندگان دیگر باقی می‌ماند.

## مرزها

- PC-B / Master Data، Branch `codex/pc-b-airline-baggage-form`، Base `origin/develop@b62054e3`.
- بدون Migration/Schema، Shared Contract، API جدید، IAM، داده عملیاتی، Dependency/Lockfile یا تغییر ماژول PC-A.
- Ticket Catalog/Reservations فقط از قرارداد پایدار فعلی مصرف می‌کنند؛ انتخاب خودکار قاعده در زمان صدور/رزرو بخشی از این Task نیست و مالک آن باید جداگانه هماهنگ شود.
