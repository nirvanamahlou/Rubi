# انتشار ترکیب گزارش و راهنمای نورا

این تحویل به Web، API اصلی، ‌API خواندنی مستقل و سرویس مکالمهٔ نورا وابسته است. کنترل انتشار با مالک فعلی ERP و قفل `/opt/rubi/avina-deploy.lock` انجام می‌شود. اتصال فعلی Groq/OpenAI، کلیدها، پایگاه داده و worker از تنظیمات عملیاتی موجود استفاده می‌کنند. این تغییر migration ندارد.

## وضعیت پیش از انتشار در ۱۴۰۵/۰۹/۰۴

| واحد | مسیر مؤثر | مشاهدهٔ بدون نشست از داخل Web |
| --- | --- | --- |
| Web | ورودی عمومی `/api/assistant/v3/conversation` به ۳۰۰۰ | بدون Origin مجاز ۴۰۳، با Origin مجاز و بدون نشست ۴۰۱ |
| API اصلی | `http://api:4000/api/v1` روی شبکهٔ داخلی Web | سلامت ۲۰۰، هویت و شرکت ۴۰۱، گزارش جدید واچر ۴۰۴ |
| API خواندنی | پراکسی عمومی `/api/v1/sales/assistant-agent/` به ۴۳۰۱ | مسیر شمارش پیشین ۴۰۱، خوانش فروش جدید ۴۰۵ |
| سرویس نورا | `https://avinaofficial.ir/v3/assistant/conversation` به ۴۳۰۰ | مکالمه ۴۰۱، مسیر جدید برنامه‌ریز ۳۰۷ به ورود Web |

در این بررسی شناسهٔ کوتاه تصویر Web برابر `765b9a9bdc1b`، API برابر `388becd04602`، خوانش برابر `0321260ad306` و نورا برابر `242b40fc436e` بود. سورس مؤثر نورا از mount مقصد `/nora-source` و راه‌انداز از `/nora-runtime.mjs` می‌آیند. انتشار قبلی قراردادها با ادغام سه‌طرفهٔ تغییرات روی تصاویر در حال اجرا انجام شده است. برچسب OCI به‌تنهایی نسخهٔ قابل مقایسه با Git را تعیین نمی‌کند.

مقایسهٔ فایل‌های اجرایی سورس با مبنای `b0f89a43d` این اختلاف‌ها را نشان داد. نمونهٔ مهم آن کنترلر پشتیبانی وب‌سایت در API عملیاتی است که در درخت این commit وجود ندارد. جایگزینی کامل تصویر، این قابلیت را در معرض حذف قرار می‌دهد.

## ساخت کاندید

1. SHA کامل مبنای پیش از تغییر و SHA نهایی دارای CI سبز را ثبت کنید. با فرمان زیر سورس مبنا را با چهار واحد در حال اجرا تطبیق دهید. نتیجه شامل مسیرهای تغییرکرده، اضافی و مفقود است. کد خروج ۱ یعنی جایگزینی تصویر کامل نیاز به بررسی دارد. این مقایسه تنها سورس را پوشش می‌دهد. برچسب انتشار، دارایی‌های استاتیک، تنظیمات و build نهایی را جداگانه بررسی کنید.

   ```powershell
   node scripts/operations/nora-agent/compare-release-source.mjs $baselineSha rubi-erp
   ```

2. با مالک آخرین نسخه، هر اختلاف مؤثر را با Git آشتی دهید و تغییراتش را در کاندید نگه دارید. در صورت وجود تغییر منتشرشدهٔ مستقل، مبنا، فایل زنده و تغییر پیشنهادی را سه‌طرفه ادغام کنید. برای تغییرات مؤثر بر منطق، آزمون همان بخش و CI مجدد لازم است. تا روشن شدن اختلاف، ترافیک واقعی روی نسخهٔ موجود می‌ماند.
3. از checkout پاک یا `git archive` همان SHA تأییدشده استفاده کنید. ساخت در runner ایزوله انجام می‌شود. برای Dockerfile مخزن، آرگومان‌های عمومی `NEXT_PUBLIC_API_BASE_URL=https://avinaofficial.ir/api/v1` و `NEXT_PUBLIC_ASSISTANT_AGENT_ENABLED=true` را بدهید. `NEXT_PUBLIC_NORA_MODEL_PLANNER_ENABLED=true` امکان فعال‌سازی برنامه‌ریز مدل در مرحلهٔ بعد را در bundle می‌سازد. پرچم سروری همچنان مستقل است. پوشهٔ public عملیاتی، فایل‌های استاتیک مورد نیاز مرورگرهای باز و mountهای جاری را حفظ کنید. بعد از build و پیش از اضافه کردن دارایی‌های قدیمی، بررسی bundle را اجرا کنید.

   ```sh
   docker build --build-arg NEXT_PUBLIC_API_BASE_URL=https://avinaofficial.ir/api/v1 \
     --build-arg NEXT_PUBLIC_ASSISTANT_AGENT_ENABLED=true \
     --build-arg NEXT_PUBLIC_NORA_MODEL_PLANNER_ENABLED=true \
     --label "org.opencontainers.image.revision=$release_sha" \
     --tag "rubi-candidate:nora-$release_sha" .
   ```

4. کاندید را در شبکهٔ مجزا با بانک آزمون و فقط یک ورودی خصوصی آزمایش کنید. مالک سرویس باید شروع کارهای زمان‌بندی‌شده، ارسال اعلان یا اتصال به پرداخت واقعی را در کاندید مهار کند. از mount خصوصی یا کلید واقعی در فرایند ساخت استفاده نکنید. چهار واحد باید یک قرارداد API و نسخهٔ سازگار داشته باشند. راه‌انداز فعلی نورا دارای اتصال ترکیبی در آلمان است و باید ماژول‌های جدید را از مسیر نسخه‌دار بخواند.

### کاندید سازگار با تغییرات عملیاتی

روی PC-C، `$stage` پوشهٔ خصوصی جدید است و هر دو شناسهٔ Git کامل‌اند. اسکریپت فقط فایل‌های کد تغییریافته را از واحدهای جاری می‌خواند. هر تعارض حل‌نشده پیش از صدور manifest کار را متوقف می‌کند. حالت `WORKTREE` برای پیش‌نمایش است.

```powershell
python scripts/operations/nora-agent/prepare-orchestration-candidate.py $baselineSha $releaseSha $stage
Copy-Item scripts/operations/nora-agent/build-orchestration-candidate.py $stage
Copy-Item scripts/operations/nora-agent/promote-orchestration.py $stage
Copy-Item scripts/operations/nora-agent/orchestration_source.py $stage
```

فقط همین پوشه را در یک مسیر جدید با دسترسی ۰۷۰۰ زیر `/opt/rubi` بارگذاری و checksum انتقال را کنترل کنید. روی سرور، `stage` به همین پوشهٔ نسخه اشاره می‌کند. ساخت به ترتیب API، خوانش و Web انجام می‌شود و هیچ‌کدام را وارد ترافیک نمی‌کند. در ۴۳۰۰، سورس کاندید جداگانه ساخته می‌شود و ورود ماژول با کاربر ۱۰۰۰ و بدون شبکه امتحان می‌شود. شناسه‌های حاصل در `built.json` ثبت می‌شوند.

```sh
python3 "$stage/build-orchestration-candidate.py" "$stage" check
python3 "$stage/build-orchestration-candidate.py" "$stage" build
for unit in api read assistant ingress web; do
  python3 "$stage/promote-orchestration.py" "$stage" check "$unit" || exit 1
done
```

پس از CI سبز همان SHA و تأیید انتشار، فرمان‌های زیر را مرحله‌به‌مرحله اجرا کنید. API اصلی کنار نمونهٔ دیگری از AppModule روی بانک عملیاتی اجرا نمی‌شود، چون AppModule پردازش‌های پس‌زمینهٔ مالی، تلفنی و رزرواسیون را راه می‌اندازد. هر فرمان فقط یک واحد را زیر قفل مشترک تغییر می‌دهد. پس از مرحلهٔ API، سلامت، مسیر قدیمی فروش و پاسخ ۴۰۱ برای درخواست بدون نشست گزارش جدید واچر بررسی شود. پس از خوانش، POST بدون نشست به مسیر جدید فروش باید از ۴۰۵ به ۴۰۱ برسد. اگر هر آزمون رد شد، همان مرحلهٔ موفق قبلی را برگردانید و ادامهٔ فعال‌سازی متوقف شود.

```sh
python3 "$stage/promote-orchestration.py" "$stage" up api
python3 "$stage/promote-orchestration.py" "$stage" up read
python3 "$stage/promote-orchestration.py" "$stage" up assistant
python3 "$stage/promote-orchestration.py" "$stage" up ingress
python3 "$stage/promote-orchestration.py" "$stage" up web
```

برای بازگشت، فقط واحدهای واقعاً فعال‌شده را از آخر به اول برگردانید. Compose همان تصویری را اجرا می‌کند که پیش از تغییر ثبت شده بود. برای دو سرویس مستقل، کانتینر قبلی با شناسه و mountهای قبلی دوباره شروع می‌شود. هر فرمان در صورت مشاهدهٔ نسخه یا پیکربندی پیش‌بینی‌نشده متوقف می‌شود.

```sh
python3 "$stage/promote-orchestration.py" "$stage" down web
python3 "$stage/promote-orchestration.py" "$stage" down ingress
python3 "$stage/promote-orchestration.py" "$stage" down assistant
python3 "$stage/promote-orchestration.py" "$stage" down read
python3 "$stage/promote-orchestration.py" "$stage" down api
```

## ترتیب فعال‌سازی

1. پیش از تغییر، زیر قفل انتشار، فعالیت هم‌زمان و شناسهٔ هر چهار تصویر، mountهای نسخه‌دار، تنظیمات Web، نگاشت nginx و سلامت قدیم را دوباره کنترل کنید. مراجع بازیابی پیش از تغییر را در فضای خصوصی انتشار نگه دارید.
2. ابتدا کاندید خوانش ۴۳۰۱ و API اصلی ۴۰۰۰، سپس سرویس ۴۳۰۰ و در آخر Web را آماده کنید. API خواندنی باید فقط مسیر POST خواندنی جدید را در allowlist داشته باشد. در Web عملیاتی، `NORA_ERP_API_BASE_URL=http://api:4000/api/v1` برای داده‌های مالک، `ASSISTANT_SERVICE_URL=https://avinaofficial.ir` برای سرویس مکالمه و `ASSISTANT_AGENT_ENABLED=true` لازم است. شبکهٔ کانتینر Web و ۴۳۰۰ جداست. آدرس loopback تنظیمات Compose محلی مخصوص namespace مشترک همان محیط است.
3. بلوک دقیق `location = /v3/assistant/plan` از [فایل مسیرهای nginx](../../scripts/operations/nora-egress/nginx-locations.conf) را به تنظیم فعال اضافه کنید. پراکسی مسیر مکالمه و کنترل Origin آن باقی می‌ماند. ابتدا `nginx -t` و اعتبارسنجی Compose با `config --quiet` انجام شود. بعد از تغییر واحدها، فرمان زیر را در PC-C اجرا کنید. خروج ۰ صرفاً پیش‌شرط آزمون حساب واقعی است.

   ```powershell
   Get-Content -Raw -Encoding utf8 scripts/operations/nora-agent/probe-orchestration.mjs | ssh rubi-erp docker exec -i rubi-production-web-1 node --input-type=module
   ```

4. با `NORA_COMPOSITION_ENABLED=false` مسیر قدیم را بررسی کنید. سپس در Web ترکیب قطعی را با `NORA_COMPOSITION_ENABLED=true` فعال کنید. برنامه‌ریز مدل را بعد از قبولی مسیر قطعی با `NORA_MODEL_PLANNER_ENABLED=true` در هر دو فرایند Web و ۴۳۰۰ فعال کنید. هر موج باید از یک نشست واقعی شروع شود. تغییر دامنهٔ کاربران نیازمند امکان مسیریابی موج در استقرار است. بدون چنین امکانی موج را ابتدا در ورودی خصوصی کاندید با همان سیاست احراز هویت اجرا کنید.

## بررسی با نشست واقعی

در مرورگر مدیر وارد ERP شوید، «همه شرکت‌ها» را در بالای صفحه تأیید کنید و از کادر عادی نورا سؤال‌ها را بفرستید. نقش، انتخاب شرکت، SHA، زمان تهران، شناسهٔ مورد و قبول/رد را ثبت کنید. محتویات قرارداد، نشانی خصوصی، شماره تماس، کوکی یا متن خام پاسخ در رسید اشتراکی درج نشود.

| مورد | سؤال یا اقدام | تطبیق با پنل |
| --- | --- | --- |
| فروش، ردیف و راهنما | «فروش دو هفته اخیر چقدر بوده و اطلاعات قراردادهای این دو هفته رو بده و بهم بگو چطور قرارداد جدید بزنم؟» | پیوند فروش را باز کنید. بازهٔ تهران، ردیف‌ها، تعداد، جمع هر ارز با همان فیلتر و راهنمای فرم ثبت را مقایسه کنید. از صفر یا دادهٔ ناقص نتیجهٔ ساختگی نگیرید. |
| ادامهٔ همان دوره | «لیست قراردادهای همون دوره رو بده» | زمان پایان در پیوند دو پاسخ باید یکسان باشد. مدت بین دو پرسش نباید جمعیت را تغییر دهد؛ تغییر واقعی رکورد در فاصلهٔ دو خوانش جداگانه ثبت شود. |
| واچر | «کدوم قراردادهای هتل تسویه شدن ولی واچر ندارن و از کجا پیگیری کنم؟» | مسیر گزارش رزرواسیون، وضعیت تسویهٔ مالی و تک‌تک اقامت‌های فاقد واچر را بررسی کنید. برای قرارداد دارای چند اقامت، داشتن واچر برای یک اقامت نباید اقامت دیگر را بپوشاند. |
| میزکار | «درخواستم الان دست کیه و از کجا پیگیریش کنم؟» | درخواست‌های حساب در میزکار، مرحله، ارجاع و مسیر راهنما مقایسه شود. اگر چند درخواست وجود دارد، انتظار انتخاب مورد به‌جای حدس نام شخص است. |
| برنامه‌ریز | یک درخواست چندبخشی با جمله‌بندی محاوره‌ای خارج از الگوی قطعی بفرستید. | زمان، قیود سؤال و تعداد بخش‌ها را مقایسه کنید. در رخداد پالایش‌شدهٔ سرویس فراخوانی واقعی برنامه‌ریز تأیید شود. |
| رگرسیون | یک سؤال راهنمای ساده، یک گزارش تک‌بخشی و صفحهٔ قرارداد با پرداخت ریالی نسخهٔ قبلی | راهنما، گزارش و مبالغ پنل با نسخهٔ مبنا تطبیق داشته باشند. |

برای پذیرش نقش‌ها، [ماتریس پرسش و قالب رسید](../assistant/WORKFLOW-COVERAGE.md) استفاده می‌شود. نتیجهٔ حساب مدیر فقط برای همان حساب معتبر است. ردیف‌های کارمند با حساب مجاز همان سمت و شرکت‌های قابل انتخاب خودش بررسی می‌شوند. نبود حساب محدود با وضعیت «در انتظار» ثبت می‌شود.

## پایش و بازگشت

در هر موج، سلامت Web/API/۴۳۰۰/۴۳۰۱، وضعیت‌های ۳۰۷/۴۰۱/۴۰۳/۴۰۵/۴۲۹/۵xx، زمان پاسخ و تعداد پاسخ‌های ناقص را با خط مبنای ثبت‌شدهٔ همان مسیر مقایسه کنید. مشاهدهٔ دادهٔ خارج از مجوز، اختلاف مبلغ یا ردیف با پنل، یا خرابی مسیرهای قبلی مانع ادامهٔ فعال‌سازی است. برای توقف الگوسازی، پرچم برنامه‌ریز را در هر دو سرویس ببندید. برای برگشت به مسیردهی قبلی، ترکیب را در Web خاموش کنید. اگر خوانش یا خود پنل رگرسیون دارد، زیر همان قفل، چهار مرجع نسخه، mount سورس نورا و فقط نگاشت‌های تغییرکردهٔ nginx را به آخرین وضعیت سالم برگردانید. تطبیق شناسه‌ها، آزمون ورودی‌ها و کنترل مسیر قبلی در مرورگر را تکرار کنید و اثر برگشت را در رسید انتشار ثبت کنید.

برای اصلاح نسخهٔ فعال، پس از آماده‌سازی از روی commit نهایی، به‌جای `build` دستور `build-updates` را اجرا کنید. سازنده تمام واحدهای دارای تغییر اجرایی در manifest را می‌سازد. پس از سبز شدن CI هر واحد تغییرکرده را به ترتیب زیر قفل با `check` و `up` فعال کنید. در صورت شکست، واحدهای قبلی این انتشار را به ترتیب معکوس با `down` بازگردانید. ابزار انتشار تنظیمات فعال قبلی Web را در رسید ثبت می‌کند تا `down web` همان تنظیمات و تصویر قبلی را بازگرداند.

در این انتشار `NORA_COMPOSITION_TELEMETRY=true` در Web فعال می‌شود. رخداد `nora.composition.part` فقط نوع ابزار، وضعیت بخش‌ها و زمان اجرا را دارد. پس از یک سؤال واقعی، تعداد و زمان این رخدادها را از خروجی پالایش‌شده بررسی کنید. بازگشت، مقدار پیشین این گزینه یا نبود آن را عیناً برمی‌گرداند.
