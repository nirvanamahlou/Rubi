# SITE-CANCELLATION-1116

The owner requests automatic ERP cancellation visibility in website history while preserving payment facts. Existing signed catalog deliveries gain cancelledOrders:[{externalId,contractId}], limited to exact configured site/branch links and native cancelled Sales contracts through a bounded public read. No personal or financial facts are transmitted. Existing product and logo contracts remain compatible. The receiver accepts only a newer signed revision, verifies both identifiers against the local linked order and changes only cancellation status/history; financial status, receipts and confirmation facts remain. Replays and stale deliveries do nothing; absence never reactivates a cancellation.

An additive trigger queues the existing durable revision atomically when a linked contract changes into CANCELLED, including a link inserted for an already-cancelled contract. Other statuses, branches and unrelated contracts do not queue it. No polling on visits and no upstream business command. Consumer site chat2 owns receiver/history UI and its guarded deployment; producer waits for receiver readiness before activation. Standing authorization covers green develop merge and scoped ERP API deployment. No real cancellation or payment is used as a test.

Validation: targeted producer/Sales-port regressions pass, including exact link/branch projection, actor refusal, bounded overflow and cancellation inclusion without product/logo dependencies. An isolated PostgreSQL fixture proves linked cancellation, repeated update, already-cancelled link, rollback and unrelated-status/branch behavior without changing production business records. Full API typecheck/build and hosted exact-head gates remain required before activation.
