# پلن اتصال آزمایشی یک سایت به RUBI / Noora

تاریخ: ۲۰۲۶-۱۰-۱۹ — مسئول اجرای Integrations: PC-D

وضعیت: طرح اجرایی پیش از دریافت دامنه. این سند تأیید اتصال یک سایت مشخص نیست. نسخهٔ کد مبنا برای به‌روزرسانی محلی: `develop@c5b267c4`. پس از دریافت دامنه، یافته‌ها و تغییرات دقیق هر دو طرف در پیوست همین طرح ثبت می‌شوند.

## نتیجه‌ای که می‌خواهیم

ابتدا فقط یک جریان مشخص و قابل آزمون از سایت تستی به RUBI برقرار شود؛ پیشنهاد برای قسطی روو «دریافت درخواست خرید اقساطی برای بررسی واحد مسئول» است. این پیشنهاد باید با امکانات واقعی سایت و قرارداد عمومی ماژول مقصد تطبیق داده شود. اتصال کامل همهٔ فرایندها، SSO و عملیات مالی خودکار، یک تحویل واحد فرض نمی‌شوند.

هیچ طرحی نبود مطلق خطا یا آسیب‌پذیری را تضمین نمی‌کند. معیار تحویل، شواهد تست، مرز دسترسی روشن، قابلیت قطع اتصال و ریسک‌های باقی‌ماندهٔ ثبت‌شده است.

## ۱. وضعیت واقعی فعلی

| بخش | وضعیت و محدودیت |
| --- | --- |
| ثبت برند و سامانه، مشخصات و روش مدنظر اتصال | قابل استفاده؛ هر برند می‌تواند چند سامانه داشته باشد |
| مجوزها، scope شعبه و سازمان، ذخیرهٔ تنظیمات و audit | از زیرساخت موجود RUBI استفاده می‌شود؛ مجوز تازه بدون نیاز و تأیید تعریف نمی‌شود |
| منوی چهارگانه و ۹ زیربخش، کارت و drill-down | موجود؛ شاخص بدون منبع معتبر «داده موجود نیست» است |
| اتصال عمومی یک سایت صرفاً با URL | عملیاتی نیست؛ ثبت دامنه درخواست خارجی ایجاد نمی‌کند |
| تست اتصال، credential reference، adapter اختصاصی و نگاشت اجرایی | برای سایت مشخص باید بررسی و تکمیل شوند |
| webhook عمومی، inbox/outbox، صف خطا و sync پایدار | برای سایت جدید متصل نیستند؛ زیرساخت و قرارداد واقعی لازم است |
| مسیرهای تخصصی Procurement و Customer Affairs | در پروژه وجود دارند؛ باید قابلیت استفادهٔ مجدد و سازگاری آن‌ها بررسی شود؛ وجودشان اثبات اتصال این سایت نیست |
| مدیریت خارجی و SSO | فعال نیست؛ مشروط به پشتیبانی و آزمون دو طرف |

## ۲. پیام بعدی چه اطلاعاتی داشته باشد؟

| ورودی | نمونه یا توضیح | دلیل |
| --- | --- | --- |
| نام برند و سامانه | قسطی روو / پنل آزمایشی | جلوگیری از اشتباه بین برند، سایت و شرکت حقوقی |
| URL سایت و URL پنل ادمین | آدرس HTTPS بدون رمز یا توکن | تشخیص مقصد؛ دامنهٔ پنل الزاماً آدرس API نیست |
| محیط | تستی، staging یا عملیاتی | جداکردن داده و مجوزهای آزمایش |
| اجازه و حدود بررسی | مشاهدهٔ پنل، خواندن API؛ عملیات آزمایشی مجاز را مشخص کن | دامنه به‌تنهایی مجوز تغییر تنظیمات، پرداخت یا حذف داده نیست |
| اولین کاربرد مطلوب | دریافت درخواست خرید اقساطی | تعیین تحویل کوچک و قابل قبول |
| مستندات API یا مسئول فنی | OpenAPI، مستندات داخلی یا دسترسی به کدِ مجاز | کشف روش واقعی اتصال بدون حدس‌زدن endpoint |
| وضعیت دادهٔ تست | نمونهٔ مصنوعی یا دادهٔ ناشناس‌شده | جلوگیری از انتقال غیرضروری اطلاعات اشخاص |
| شرکت و شعبهٔ مقصد در RUBI | شناسهٔ قابل انتخاب از منابع موجود | هر اتصال باید محدودهٔ مالکیت و دسترسی مشخص داشته باشد |

رمز مدیر، API secret یا فایل محیط را در متن پلن یا Git قرار نده. برای ورود پنل از حساب تستی محدود یا ورود تعاملی استفاده می‌کنیم؛ دسترسی API مخصوص سرویس از کانال امن در محل امن سمت سرور تنظیم می‌شود. ایجاد یا گسترش دسترسی، انتشار endpoint عمومی و تغییرات سمت سایت باید در محدودهٔ مجاز همان مرحله باشند.

## ۳. مسیر مرحله‌به‌مرحله پس از دریافت دامنه

### مرحله صفر: تثبیت محیط و خط مبنا

- commit، image، نسخهٔ API و وضعیت migration دو طرف ثبت می‌شود.
- محیط تست از production، credentialها، صف‌ها و داده‌های آن جدا می‌شود.
- snapshot/backup قابل بازیابی و روش rollback مشخص می‌شود؛ دادهٔ عملیاتی برای ساخت محیط آزمایش کپی نمی‌شود مگر با مجوز و حداقل‌سازی لازم.
- فهرست اتصال‌ها و adapterهای موجود بررسی می‌شود تا اتصال موازی یا تکراری ساخته نشود.

خروجی: شناسنامهٔ محیط و دامنهٔ مجاز کار. شرط عبور: مقصد، مالک و امکان بازیابی معلوم باشند.

### مرحله یک: بررسی مجاز و فقط‌خواندنی پنل

۱. آدرس، HTTPS، گواهی معتبر و تغییرمسیرهای واقعی بررسی می‌شوند.
۲. با حساب تستی مجاز، امکانات مستند پنل/API، نسخه، وب‌هوک و SSO بررسی می‌شوند.
۳. موجودیت‌ها، وضعیت‌ها، ارز، منطقهٔ زمانی، صفحه‌بندی، نرخ درخواست و محدودیت‌ها ثبت می‌شوند.
۴. هیچ اسکن تهاجمی، دورزدن MFA/CAPTCHA، حدس رمز یا عملیات تجاری انجام نمی‌شود.

خروجی: جدول قابلیت‌های «تأییدشده / پشتیبانی‌نشده / نیازمند بررسی» و شواهد بدون secret یا PII. اگر فقط پنل HTML وجود دارد، اتصال API موجود فرض نمی‌شود و به‌صورت پیش‌فرض scraping یا اشتراک session جای آن را نمی‌گیرد.

### مرحله دو: گزارش فاصله و انتخاب یک جریان

برای هر نیاز، تغییر لازم در سایت و RUBI جدا ثبت می‌شود. اگر API وجود دارد adapter سازگار ساخته می‌شود. اگر API وجود ندارد، ابتدا قرارداد endpoint و رویداد به تیم سایت تحویل داده می‌شود. اگر قرارداد عمومی ماژول مقصد در RUBI موجود نیست، producer آن باید با مالک ماژول هماهنگ شود؛ Integrations مستقیماً سراغ جدول او نمی‌رود.

خروجی: فایل تغییرات دقیق با مسیر فایل/endpoint، owner، وابستگی، اولویت، تست و معیار پذیرش. زمان‌بندی قطعی پس از این کشف برآورد می‌شود.

### مرحله سه: قرارداد داده و مالکیت

| داده یا تصمیم | مالک قطعی در RUBI | نقش Integrations |
| --- | --- | --- |
| هویت مشتری و رفع تطبیق مبهم | Customers | نگاشت شناسهٔ خارجی و تحویل درخواست از قرارداد عمومی |
| قرارداد و تخصیص تجاری | Sales | انتقال داده؛ بدون ایجاد قرارداد موازی |
| رزرو، صدور و لغو | Reservations | مصرف قابلیت و تحویل ورودی؛ بدون تصمیم تجاری مستقل |
| تأیید پرداخت، اعتبار و آزادسازی | Finance | تحویل ادعا و مرجع خارجی برای بررسی |
| کاربر، نقش، نشست و دسترسی | IAM | مصرف هویت و مجوز موجود؛ بدون کاربر موازی |
| اعلان | Notifications | درخواست اعلان به گیرندهٔ مجاز از سرویس عمومی |

قرارداد نسخه‌دار شامل فیلدهای الزامی/اختیاری، nullable، enum، اعتبارسنجی، خطاها و سیاست سازگاری است. مبلغ به صورت رشتهٔ Decimal و کد ارز منتقل می‌شود؛ ریال و تومان با واحد صریح، بدون تبدیل یا جمع مبهم. زمان‌ها UTC با offset مشخص و شناسه‌ها پایدارند. نمونه‌ها مصنوعی‌اند. تطبیق مشتری با نام، یا ادغام خودکار موارد مبهم مجاز نیست.

خروجی: قرارداد v1 و تأیید producer/consumer. خبر «پرداخت/رزرو موفق» از سایت فقط ورودی قابل بررسی است.

### مرحله چهار: اتصال حداقلی و امن

- یک حساب سرویس با حداقل مجوز، ابتدا فقط خواندن، در محیط تست استفاده می‌شود.
- credential خارج از Git و مرورگر ذخیره می‌شود؛ DB/config فقط reference امن و نسخهٔ کلید را نگه می‌دارد. نمایش دوبارهٔ secret، ثبت در log یا افزودن به URL ممنوع است.
- دامنه، scheme و port مقصد allowlist دقیق دارند. کلاینت خروجی URL دلخواه را fetch نمی‌کند؛ DNS/IP و مقصد واقعی اتصال اعتبارسنجی می‌شوند و redirect پیش‌فرض غیرفعال است. loopback، private، link-local، metadata و IPv4/IPv6 نامجاز مسدودند. محیط داخلی تست فقط از مسیر اختصاصی و محدود مجاز می‌شود، نه با خاموش‌کردن سراسری حفاظت SSRF.
- بررسی TLS خاموش نمی‌شود. timeout، سقف حجم پاسخ، تعداد صفحه، نرخ درخواست و هم‌زمانی محدود و قابل تنظیم هستند.
- endpoint آزمایشی غیرمخرب بررسی می‌شود؛ سلامت ارتباط با موفقیت عملیات تجاری یکی نیست.
- مصرف‌کنندهٔ API در سطح سامانه/اتصال، عملیات و scope شرکت/شعبه مجوز سمت سرور دارد؛ مخفی‌کردن دکمه کافی نیست.

خروجی: تست ارتباط موفق با شواهد و بدون ایجاد سفارش/پرداخت واقعی. این مرحله به معنی آماده‌بودن sync کامل نیست.

### مرحله پنج: دریافت پایدار و webhook یا polling

envelope پیشنهادی:

```json
{
  "eventId": "synthetic-event-001",
  "eventType": "purchase-request.created",
  "schemaVersion": "1",
  "sourceSystem": "test-system-reference",
  "externalId": "synthetic-request-001",
  "occurredAt": "2026-10-19T10:00:00Z",
  "receivedAt": "2026-10-19T10:00:01Z",
  "correlationId": "synthetic-correlation-001",
  "entityVersion": "1"
}
```

این نمونه قرارداد نهایی نیست. `receivedAt` را RUBI تعیین می‌کند؛ `sourceSystem` از credential معتبر به اتصال bind می‌شود و payload باید با آن سازگار باشد. `entityVersion` یا ترتیب معتبر منبع برای جلوگیری از عقب‌رفتن وضعیت لازم است؛ timestamp به‌تنهایی برای تمام موارد کافی نیست.

- امضای توافق‌شده روی raw body و timestamp، مقایسهٔ امن، key ID، rotation و پنجرهٔ زمانی محدود لازم است؛ مقدار اولیهٔ پنجره مثلاً ۵ دقیقه و وابسته به توافق و همگامی ساعت است.
- زمان امضای هر تحویل از occurredAt رویداد جداست؛ ارسال مجدد می‌تواند امضای تازه داشته باشد، اما eventId و کلید idempotency ثابت می‌مانند. پنجرهٔ امضا نباید صرفاً به‌علت دیررس‌بودن یک رویداد معتبر آن را رد کند.
- محدودیت اندازه، content-type و schema پیش از پردازش اعمال می‌شود. secret جدا برای هر اتصال/محیط است؛ IP allowlist به‌تنهایی احراز هویت نیست.
- پیام معتبر ابتدا در inbox پایدار ذخیره و سپس ACK می‌شود؛ ACK به معنی تأیید مالی یا انجام رزرو نیست.
- uniqueness در محدودهٔ اتصال/محیط/eventId، همراه fingerprint محتوای معتبر و کنترل هم‌زمانی از اثر تکراری جلوگیری می‌کند. eventId یکسان با محتوای متفاوت خطا و audit می‌شود.
- تحویل به ماژول مالک از قرارداد عمومی و با کلید idempotency پایدار انجام می‌شود؛ crash پس از commit مقصد و پیش از ACK نباید اثر تجاری را تکرار کند. ادعای exactly-once سراسری نداریم.
- خطای موقت مانند timeout/429/5xx با backoff و jitter و رعایت Retry-After تکرار می‌شود؛ سیاست اولیه حداکثر ۵ تلاش است و پس از تست تنظیم می‌شود. خطای schema/مجوز به retry بی‌پایان نمی‌رود.
- پیام‌های شکست‌خورده در صف خطا با دلیل امن می‌مانند؛ بازپردازش فقط با مجوز، علت و audit است و امضای نامعتبر را به پیام معتبر تبدیل نمی‌کند.

بدنهٔ دارای اطلاعات شخصی فقط در حد نیاز، با رمزگذاری و دسترسی محدود در inbox/صف خطا نگهداری می‌شود؛ دورهٔ نگهداری، پاک‌سازی مجاز، حذف امن از log و نسخهٔ کلید پیش از فعال‌سازی مشخص می‌شوند. audit شامل عامل، زمان، نتیجه و تغییرات امن است، نه secret یا بدنهٔ کامل مشتری.

اگر وب‌هوک پشتیبانی نشود، polling افزایشی با cursor/checkpoint پایدار، صفحه‌بندی و هم‌پوشانی کنترل‌شده جایگزین می‌شود. checkpoint فقط پس از ثبت پایدار/تحویل موفق جلو می‌رود. قفل lease و fencing/version از sync متعارض جلوگیری می‌کنند. حذف در سایت فقط با tombstone معتبر و سیاست مالک معنا دارد؛ نبودن رکورد در یک پاسخ ناقص یا قطعی، مجوز حذف دادهٔ قبلی نیست.

پنل محلی `127.0.0.1` برای سایت بیرونی قابل دسترسی نیست. برای webhook واقعی، یک endpoint تست HTTPS محدود و مصوب لازم است. tunnel عمومی خودکار ساخته نمی‌شود و پنل مدیریت/DB/Redis عمومی نمی‌شوند. تا آماده‌شدن این مسیر، تست inbound با fixture محلی یا polling مجاز انجام می‌شود.

### مرحله شش: یک سناریوی انتهابه‌انتها

۱. یک درخواست مصنوعی در سایت تست ایجاد یا از fixture تأییدشده دریافت می‌شود.
۲. شناسهٔ خارجی، اتصال و correlation در همهٔ مراحل حفظ می‌شوند.
۳. درخواست از قرارداد ماژول مالک عبور می‌کند و نتیجهٔ واقعی ثبت می‌شود.
۴. همان پیام چند بار و هم‌زمان ارسال می‌شود؛ فقط یک اثر مجاز ایجاد شود.
۵. قطعی مقصد و restart worker آزمایش می‌شود؛ پیام گم نشود و وضعیت صحیح قبلی حفظ شود.
۶. نتیجه در صفحهٔ سامانه، تاریخچه و drill-down با دسترسی درست دیده شود.

خروجی: گزارش پذیرش با eventId، نتیجه و مدرک امن. KPI تنها از grain و منبع تأییدشدهٔ مالک محاسبه می‌شود؛ replay، چند ارز یا چند رویداد یک سفارش نباید شمارش و مبلغ را تکثیر کند. آکادمی از فروش مستقیم سفر خارج می‌ماند.

### مرحله هفت: SSO، فقط در صورت نیاز و پشتیبانی

ورود یکپارچه یک جریان مستقل از انتقال سفارش است. ابتدا مشخص می‌کنیم IAM موجود چه نقش IdP/RP قابل پشتیبانی دارد و سایت از OIDC یا SAML معتبر پشتیبانی می‌کند یا به تغییر نیاز دارد. وجود دامنه یا فرم ورود اثبات پشتیبانی نیست.

در صورت انتخاب OIDC، مسیر Authorization Code با PKCE، redirect URI دقیق، کنترل state/nonce و اعتبارسنجی issuer، audience، امضا و عمر token طراحی و تست می‌شود. هویت با issuer+subject نگاشت می‌شود؛ نام یا ایمیل تأییدنشده موجب اتصال حساب‌ها نمی‌شود. نقش ادمین خودکار اعطا نمی‌شود. عدم مجوز، خروج، انقضای نشست و لغو دسترسی آزمون دارند.

session و cookie RUBI با سایت به اشتراک گذاشته نمی‌شود؛ رمز کاربر ذخیره نمی‌شود و access/ID token در URL ارسال نمی‌شود. authorization code کوتاه‌عمر پروتکل، جایگزین token قابل استفادهٔ مستقیم نیست و باید طبق پروتکل محافظت و مبادله شود. iframe راه‌حل پیش‌فرض نیست. بدون پیاده‌سازی و آزمون دو طرف، برچسب SSO فعال نمایش داده نمی‌شود.

### مرحله هشت: انتشار محدود و امکان توقف

- اتصال پیش‌فرض غیرفعال؛ فعال‌سازی ابتدا برای یک سامانه، یک scope و یک جریان.
- معیار اولیهٔ پذیرش: صفر اثر تجاری تکراری در سناریوهای تست، صفر عبور غیرمجاز scope، صفر secret در پاسخ/log، و تطبیق همهٔ fixtureهای توافق‌شده. latency و نرخ موفقیت هدف پس از حجم واقعی تعیین می‌شوند.
- پایش backlog، خطا، آخرین موفقیت، تأخیر، replay و اعتبار credential با معنای روشن برقرار می‌شود؛ نبود داده با صفر و نامرتبط فرق دارد.
- runbook شامل قطع اتصال، pause worker، rotation کلید، بازپردازش مجاز و بازیابی checkpoint است. قطع اتصال سوابق را حذف نمی‌کند.
- rollback کد از rollback داده جداست؛ اثر مالی یا صدور واقعی با rollback خام دیتابیس پاک نمی‌شود و فقط از فرایند جبرانی مالک عبور می‌کند.
- فعال‌سازی production، پرداخت/صدور واقعی، migration مخرب، تغییر دسترسی حساس یا عمومی‌کردن سرویس‌ها نیازمند مجوز صریح همان اقدام است.

## ۴. فهرست اولیهٔ تغییرات مورد انتظار

این جدول backlog قطعی یک سایت نیست؛ پس از مرحلهٔ کشف، هر ردیف به «موجود و آزموده / نیازمند تغییر / نامرتبط / مسدود» تبدیل می‌شود.

| حوزه | تغییر احتمالی RUBI | تغییر یا ورودی سمت سایت | شرط پایان |
| --- | --- | --- | --- |
| registry و UI | قابلیت adapter، وضعیت تنظیم‌شدن، تست اتصال و پیام خطای قابل فهم | نام/محیط/مستندات | تفاوت ثبت سایت و اتصال واقعی واضح باشد |
| credential | reference امن، rotation و دسترسی محدود | سرویس اکانت یا OAuth client محدود | secret در مرورگر/API/log دیده نشود |
| adapter | کلاینت نسخه‌دار، timeout/rate/retry و SSRF guard | API مستند و پایدار | تست واقعی محدود در محیط تست |
| نگاشت | شناسهٔ خارجی، provenance و قواعد تبدیل | شناسه‌ها و وضعیت‌های پایدار | تطبیق مبهم متوقف شود |
| رویداد | inbox/outbox، signature/replay و consumer مجاز | webhook امضاشده یا API تغییرات | تحویل پایدار و اثر غیرتکراری |
| sync | checkpoint، lease، backfill محدود و reconciliation | cursor/version/tombstone | restart و دادهٔ دیررس درست مدیریت شوند |
| ماژول مقصد | استفاده یا تکمیل قرارداد عمومی با owner | دادهٔ حداقلی مطابق قرارداد | تصمیم تجاری در ماژول صاحب آن بماند |
| پایش | سوابق امن، سلامت و KPI با منبع معتبر | event/reference قابل پیگیری | drill-down به نتیجهٔ واقعی برسد |
| SSO اختیاری | هماهنگی IAM و نگاشت هویت/مجوز | OIDC/SAML معتبر | ورود، انقضا و منع دسترسی آزموده شوند |

Migration و تغییر قرارداد/وابستگی، اگر لازم شوند، پیش از اجرا جدا رزرو و با producer/consumer و مالک قفل هماهنگ می‌شوند. این سند آن قفل‌ها یا انتقال مالکیت را ایجاد نمی‌کند.

## ۵. ماتریس تست و توقف

| دسته | تست ضروری | انتظار |
| --- | --- | --- |
| احراز هویت | کلید غلط/منقضی/لغوشده، امضای دستکاری‌شده، timestamp قدیمی/آینده | رد پیام، بدون اثر تجاری و بدون افشای secret |
| scope | تعویض شناسهٔ سایت/شرکت/شعبه، دسترسی خواندن در عملیات نوشتن | منع سمت سرور |
| شبکه | redirect نامجاز، DNS rebinding، IPv6/metadata/private، پاسخ حجیم/کند | توقف امن و timeout محدود |
| دوام | crash پیش/پس از ذخیره، crash پس از commit مقصد، قطعی صف/DB، retry exhausted | عدم گم‌شدن پیامِ ACKشده و عدم اثر مضاعف |
| ترتیب | رویداد قدیمی پس از جدید، نسخهٔ برابر با payload متفاوت | جلوگیری از عقب‌رفتن وضعیت و ثبت تعارض |
| sync | دو worker، lease منقضی، صفحهٔ ناقص و checkpoint خراب | عدم اجرای متعارض و عدم حذف دادهٔ صحیح |
| تجارت | خبر جعلی پرداخت/رزرو، currency نامعلوم، مشتری مبهم | ارجاع به owner و توقف تصمیم خودکار نامعتبر |
| گزارش | replay و چند رویداد یک سفارش، چند ارز، دادهٔ ناموجود | شمارش/مبلغ بدون تکثیر و بدون جمع مبهم |
| UI | loading/empty/error/forbidden/not configured، RTL و موبایل | نمایش روشن و بدون موفقیت ساختگی |
| SSO | state/nonce/issuer/audience نادرست، code reuse و role escalation | رد ورود یا دسترسی نامجاز |

هر شکست بحرانی امنیت، یکپارچگی مالی/رزرو یا جداسازی scope مانع فعال‌سازی است. با دادهٔ نمونهٔ محدود، ادعای سلامت همهٔ شرایط production نمی‌کنیم.

## ۶. بستهٔ تحویل پس از بررسی دامنه

- گزارش قابلیت‌های واقعی پنل و محدودیت‌های دسترسی.
- فهرست تغییرات جداگانهٔ RUBI و سایت، owner و وابستگی هرکدام.
- قرارداد API/Event و نمونهٔ مصنوعی، نگاشت و سیاست خطا.
- threat model کوتاه، روش نگهداری secret و جدول permission/scope.
- برنامهٔ فازبندی و برآورد پس از کشف، بدون وعدهٔ زمان قبل از شناخت API.
- تست‌ها، شواهد، runbook توقف/بازیابی و معیار Go/No-Go.
- جدول نهایی «عملیاتی / آمادهٔ اتصال / وابسته به دسترسی خارجی یا owner».
